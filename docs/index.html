A Weekend on the Pydantic Stack

DX & product feedback from building a deep-research agent — solo, on mobile, through a Claude Code agent.

A dev spent a weekend building deepresearch — a wave-based, claim-verifying research agent — with one real question: could the full Pydantic stack (AI, Logfire, Evals, Gateway) be a production setup? Constraints were deliberately tight: one Anthropic key, one Logfire account, no other paid services, and a builder journal kept every session to capture the experience.

Verdict

The stack cleared the bar. Every prod-critical unknown got a yes — server tools work through the Gateway, costs are real and small (~$0.66 live total; the entire 10-phase hardening effort ran at $0), Logfire needed zero config, and the whole thing is offline-testable. The one true adoption blocker is subscription billing; everything else below is papercuts and onboarding polish.

Pydantic AI

The core delivered

  • winModel-less agent singletons + per-run model= kept all routing in config.
  • winGenerics carry output types end-to-end — one correct annotation fixed 45 of 51 type errors at once.
  • winOutput validators + ModelRetry are the right home for semantic rules.
  • askTestModel rejects built-in tools — the native_tools=[] override is THE pattern for offline-testing tool agents, and it's undocumented.
  • askShared RunUsage is also the limit surface — reusing one accumulator for accounting silently makes UsageLimits cumulative across sibling runs (a real bug we hit).
  • askNo per-run context to output validators — they see only ctx.deps, forcing a stash-on-mutable-Deps hack; an Agent.run(context=…) kwarg would fix it.
  • blockerCan't bill to a Claude Max subscription — shaped the entire project's economics.

Logfire

Zero-config, and a testing superpower

  • winLit up with zero extra config beyond the token.
  • wininstrument_pydantic_ai traced every call without HTTP-level noise.
  • winThe find of the effort: HasMatchingSpan + SpanQuery assert pipeline shape from the span tree offline, in CI — behavioral evals at $0.
  • askGotcha: logfire.configure() must run before dataset.evaluate sets up recording, or you get SpanTreeRecordingError.

Pydantic Evals

Near-zero friction, one sharp edge

  • winCustom evaluators are just dataclasses returning dicts — the whole objective suite was about an hour.
  • winReturning the task's typed RunRecord instead of scraping output paid off repeatedly.
  • askThe LLMJudge OpenAI default is a runtime trap — with no OpenAI key it crashes every eval run, at runtime, not construction.
  • askMinor docs drift: Dataset(...) requires name=; result.usage is an attribute, not a method.

Gateway

The open questions, closed

  • winServer-side web tools work through the Gateway (the headline unknown), verified end-to-end — it "just worked" with only its own key, no Anthropic-key juggling.
  • wingenai-prices (first-party, offline snapshot) priced every model including cache tokens and dated transitions — retired two hand-rolled workarounds.
  • askA gateway key without an encoded region breaks base-URL inference.
  • askNo max_retries knob on gateway_provider — we post-set provider.client.max_retries.

Onboarding · human DX

The friction wasn't the code

My only task outside Claude Code was signing up on the Pydantic web console — and that's exactly where the weekend slowed down. The default project came pre-created, genuinely helpful; everything after it had drag.

  • askFinding where to create a token was hard, and the credential taxonomy confuses — write token vs. read token vs. API key, with no signal for which one you actually need.
  • askCopying values by hand into Claude Code's env was painful on mobile — small targets, cross-app paste, easy to fumble.
  • noteThe velocity mismatch is the real story: inside Claude Code I move at 100×, then hit the web console and slow to a crawl — that context-switch is where drop-off risk lives.
  • askFixes: cut time-to-token, label credentials by use case, make the console mobile-first — ideally a smoother token handoff straight into a dev environment.

Agent DX · Claude's own account

Building it as an agent

Two properties of the stack made it genuinely good to build on as an agent, and one class of bug made it hard.

  • noteIntrospectable beats documented. Reading the installed package's signatures and source (Agent.override's native_tools=, the RunUsage coupling) beat any tutorial, because training data and blog posts drift monthly.
  • winOffline-testability is the superpower. TestModel/FunctionModel, ALLOW_MODEL_REQUESTS=False, and key-free evals let me verify my own work deterministically across dozens of iterations without spending a cent.
  • noteRuntime traps are what hurt. The costliest bugs failed at runtime, not construction — the LLMJudge default, the RunUsage coupling, and worst, a real env key silently making un-overridden agents network-capable (a hang I chased for a while).
  • askThe generalizable ask: fail at construction, not first request, and put the escape hatch in the error message.

Priorities

Top DX asks

  1. Faster time-to-token, clearer credential types (read vs. write vs. API key), mobile-first console — the biggest human friction.
  2. Claude Max / subscription billing — the one true adoption blocker.
  3. Agent.run(context=…) for per-run data into output validators.
  4. LLMJudge should default to the configured provider and fail at construction, not runtime.
  5. Document TestModel + built-in tools (native_tools=[]) — and put the hint in the error message.
  6. Retry config on gateway_provider; document the RunUsage / UsageLimits coupling.
