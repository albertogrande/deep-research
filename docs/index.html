A Weekend on the Pydantic Stack

The weekend had one question: could I build a real research agent on the full Pydantic stack (AI, Logfire, Evals, Gateway), solo, on mobile, with Claude Code? So I built deepresearch, a wave-based, claim-verifying agent, to find out.

Code and full journal: github.com/albertogrande/deep-research

Verdict

Yes, on every count that mattered: server tools work through the Gateway, costs are real and small (~$0.66 live total, the 10-phase hardening effort at $0), Logfire needs zero config, and the whole thing is offline-testable. Nothing here blocks adoption; the whole build ran on a normal API key. What's left is papercuts, onboarding polish, and one nice-to-have: subscription billing, to spend even less.

Pydantic AI

The core delivered

Type-safe agents end to end, routing kept in config, and three sharp edges worth filing.

  • winModel-less agent singletons + per-run model= kept all routing in config.
  • winGenerics carry output types end-to-end: one correct annotation fixed 45 of 51 type errors at once.
  • winOutput validators + ModelRetry are the right home for semantic rules.
  • gapTestModel rejects built-in tools. The native_tools=[] override is the pattern for offline-testing tool agents, and it's undocumented. Entry 2 ↗
  • gapShared RunUsage is also the limit surface: reusing one accumulator for accounting silently makes UsageLimits cumulative across sibling runs (a real bug I hit). Entry 9 ↗
  • gapNo per-run context reaches output validators: they see only ctx.deps, forcing a stash-on-mutable-Deps hack. An Agent.run(context=…) kwarg would fix it. Entry 5 ↗

Pydantic Logfire

Logfire did double duty

Zero config to stand up, then span queries turned it into an offline test tool.

  • winLit up with zero extra config beyond the token.
  • wininstrument_pydantic_ai traced every call without HTTP-level noise.
  • winThe find of the effort: HasMatchingSpan + SpanQuery assert pipeline shape from the span tree offline, in CI. Behavioral evals at $0.
  • gapGotcha: logfire.configure() must run before dataset.evaluate sets up recording, or you get SpanTreeRecordingError. Entry 22 ↗

Pydantic Evals

Evals came almost for free

Custom evaluators are just dataclasses; one runtime default is the only real trap.

  • winCustom evaluators are just dataclasses returning dicts: the whole objective suite took about an hour.
  • winReturning the task's typed RunRecord instead of scraping output paid off repeatedly.
  • gapThe LLMJudge OpenAI default is a trap: with no OpenAI key it crashes every eval run at runtime, not at construction. Entry 7 ↗
  • gapMinor docs drift: Dataset(...) requires name=; result.usage is an attribute, not a method. Entry 7 ↗

Pydantic AI Gateway

The Gateway closed the open questions

Server tools ran end to end on one key, and first-party pricing retired my hacks.

  • winServer-side web tools work through the Gateway (the headline unknown), verified end-to-end. It "just worked" with only its own key, no Anthropic-key juggling.
  • wingenai-prices (first-party, offline snapshot) priced every model including cache tokens and dated transitions, retiring two hand-rolled workarounds.
  • gapA gateway key without an encoded region breaks base-URL inference. Entry 17 ↗
  • gapNo max_retries knob on gateway_provider: I post-set provider.client.max_retries. Entry 17 ↗
  • gapModel calls can't bill to a Claude Max subscription. An API key works fine for companies and solo devs alike; subscription billing would just cut cost for heavy personal use. Entry 0 ↗

Human Experience

The friction wasn't the code

Everything inside Claude Code flew; the web-console signup is where the weekend slowed.

  • winThe default project came pre-created, a small thing that genuinely helped.
  • gapFinding where to create a token was hard, and the credential taxonomy confused me: write token vs. read token vs. API key, with no signal for which one you actually need. Entry 26 ↗
  • gapCopying values by hand into Claude Code's env was painful on mobile: small targets, cross-app paste, easy to fumble. Entry 26 ↗
  • gapFixes: cut time-to-token, label credentials by use case, make the console mobile-first, and ideally hand the token straight off into a dev environment. Entry 26 ↗
  • noteThe velocity mismatch is the real story: inside Claude Code I move at 100×, then hit the web console and slow to a crawl. That context switch is where drop-off risk lives.

Agent Experience

The stack builds well as an agent

Introspectable APIs and offline testing made it a delight; runtime-only traps were the pain.

  • winOffline-testability is the superpower. TestModel/FunctionModel, ALLOW_MODEL_REQUESTS=False, and key-free evals let me verify my own work deterministically across dozens of iterations without spending a cent.
  • gapThe fix that generalizes: fail at construction, not first request, and put the escape hatch in the error message. Entry 26 ↗
  • noteRuntime traps are what hurt. The costliest bugs failed at runtime, not construction: the LLMJudge default, the RunUsage coupling, and worst, a real env key silently making un-overridden agents network-capable (a hang I chased for a while).
  • noteIntrospectable beats documented. Reading the installed package's signatures and source (Agent.override's native_tools=, the RunUsage coupling) beat any tutorial, because training data and blog posts drift monthly.

Priorities

Where I'd start

Ordered by adoption impact, from biggest lever to smallest polish.

  1. Cut time-to-token, clarify credential types (read vs. write vs. API key), and make the console mobile-first: the biggest human friction. Entry 26 ↗
  2. Add Agent.run(context=…) so per-run data reaches output validators. Entry 5 ↗
  3. Default LLMJudge to the configured provider, and fail at construction, not runtime. Entry 7 ↗
  4. Document TestModel + built-in tools (native_tools=[]), and put the hint in the error message. Entry 2 ↗
  5. Add retry config to gateway_provider, and document the RunUsage / UsageLimits coupling. Entry 17 ↗ Entry 9 ↗
  6. Support subscription billing (e.g. Claude Max) so heavy users spend less: a nice-to-have, not a blocker. Entry 0 ↗
